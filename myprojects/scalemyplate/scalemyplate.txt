## 3. Project Description (long form — for the case-study page)

ScaleMyPlate is a cross-platform mobile app built with React Native (Expo) and a Supabase
backend that acts as the companion app for an IoT smart kitchen scale.

Most calorie-tracking apps make the user do the hard part: guessing portion sizes. ScaleMyPlate
removes that step. The physical scale weighs the food, identifies it (via a USDA food database
lookup or a product barcode), and pushes the meal straight into the cloud — where the mobile app
picks it up. The user gets accurate calories, protein, carbs and fat without typing a thing,
plus the option to log food manually when the scale is not around.

The app covers the full product surface: email/password and social authentication, a guided
onboarding flow, a QR-code pairing flow to link a phone to a physical scale, a daily nutrition
dashboard, manual food entry, a full meal history with per-food editing, goal setting with
weekly analytics, streak tracking, light/dark theming, and account management including a
complete cascading account deletion.

On the backend, I designed the PostgreSQL schema and built **14 Supabase Edge Functions** that
serve as a documented REST API — consumed both by the mobile app and directly by the IoT device
firmware. Postgres triggers keep meal totals, daily summaries and user streaks consistent
automatically, so nutrition maths never has to be duplicated between the device and the app.
Every user-owned table is protected by Row Level Security policies.

## 4. Key Features (bullet list for the site)

- **Smart-scale integration** — the IoT scale submits weighed meals straight to the cloud API; the app reflects them on next load.
- **QR-code device pairing** — scan a QR code shown on the scale to link a phone to a device (up to 2 user profiles per scale).
- **Barcode scanning** — look up packaged products by barcode through the OpenFoodFacts database.
- **USDA food search** — full-text search over the USDA food database, ranked by popularity so common foods surface first.
- **Manual food logging** — add any food with serving size, actual consumed weight and macros; nutrition auto-scales to the weight eaten.
- **Daily dashboard** — calories-remaining ring, macro breakdown, last meal, quick actions.
- **Meal history** — browse any past date, expand meals, edit or delete individual food items with totals recalculated automatically.
- **Goals and analytics** — set calorie/protein/carb/fat targets and view weekly breakdowns (this week / last week / 2 weeks ago) with totals and daily averages.
- **Streak tracking** — current and longest logging streaks, maintained by database triggers.
- **Full theming** — hand-built light and dark themes with a shared colour system and custom SVG tab icons.
- **Account management** — password reset flow, personal details, notification preferences, and full account deletion.

## 6. Architecture (one paragraph + optional diagram)

Three clients share one backend: the **mobile app**, the **IoT scale**, and the **Supabase
PostgreSQL database** that both talk to.

```
+----------------+          +----------------------+          +----------------+
|  IoT Smart     |  REST    |  Supabase Edge       |   SQL    |  PostgreSQL    |
|  Scale         | -------> |  Functions (Deno)    | -------> |  + RLS         |
|  (firmware)    |          |  14 endpoints        |          |  + triggers    |
+----------------+          +----------------------+          +-------+--------+
                                                                      |
+----------------+                Supabase JS client                  |
|  React Native  | <--------------------------------------------------+
|  App (Expo)    |        auth - reads - writes
+----------------+

        OpenFoodFacts API  +
        USDA FoodData      +--> cached in PostgreSQL
```

- The **app** authenticates with Supabase Auth and reads/writes user data through a typed
  data-access layer, with RLS enforcing ownership at the database level.
- The **scale** has no user session, so it uses the Edge Function API (`/iot-meal`,
  `/profile-data`, `/device-register`, and so on) with a service key.
- **Postgres triggers** recompute meal totals, daily summaries and streaks whenever a food item
  changes — so the app, the device and the API can never drift out of sync.

## 7. Database Design (optional "under the hood" section)

9 core tables, all with Row Level Security:

`profiles` · `user_goals` · `user_streaks` · `devices` · `device_users` ·
`meals` · `food_items` · `daily_summaries` · `usda_foods`

Highlights worth calling out:
- Auto-provisioning triggers create a profile, default goals and a streak row on signup.
- A trigger chain recalculates meal totals, then the daily summary, then the streak on every
  food-item write.
- `device_users` enforces a maximum of 2 profiles per physical scale with automatic slot assignment.
- Food search uses a GIN full-text index plus a click-popularity counter for result ranking.

## 9. Challenges / What I am proud of (for the case-study narrative)

Pick one or two of these if the layout has a "Challenges" or "Highlights" section:

1. **Keeping two clients in sync.** The scale and the app can both modify the same meal. Instead
   of duplicating nutrition maths in firmware and in the app, I pushed all derived values
   (meal totals, daily summaries, streaks) into Postgres triggers — one source of truth, and
   both clients stay correct for free.
2. **Designing an API for hardware.** The IoT device has no user session and limited memory, so
   `/profile-data` returns goals, streak, history and the current day's meals in a single round
   trip rather than forcing the firmware to make five calls.
3. **Portion accuracy.** Nutrition is stored per reference serving and scaled by the actual
   weighed amount, so a 150g portion of a food listed per 100g is computed exactly — the whole
   reason the scale exists.
4. **A hand-built design system.** No UI kit — custom SVG tab icons, a shared colour token
   system, and a full light/dark theme implemented across roughly 9,000 lines of screen code.
